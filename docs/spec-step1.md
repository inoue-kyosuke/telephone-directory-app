## 1. 概要・目的・成功イメージ

### 1.1 概要
代表電話にかかってきた電話について、「つなぐ/つながない」の判断と、取次メモの記録を支援する社内Webアプリ。取引先担当者の氏名・電話番号などの個人情報を扱う。

### 1.2 目的【補足】
- 営業電話など優先度の低い電話への対応時間を減らす(受ける側・つなぎ先の両方)。
- 電話を受けた人が、かかってきた電話の優先度をその場で判断できる。
- 新人が誰にも聞かずに対応できる。

### 1.3 成功イメージ【補足】
新人が、かかってきた相手を検索するだけで「誰につないでよいか/つながないか」を確認でき、つながない場合や取次先が不在の場合は取次メモを残して終えられる。取次先の人は、自分宛ての未対処の取次メモを一覧で確認できる。DMやSlackチャンネルでの手書きの連絡が不要になる。

注: ヒアリングの課題にある「電話でどう答えるか(応対トーク・テンプレート)」はSTEP1の対象外(2.2、Q-15)。STEP1の成功は「つなぐ/つながないの判断」と「取次メモ」に限る。

## 2. スコープ

### 2.1 STEP1の対象【決定】
1. 会社・担当者の登録/編集/削除(復元含む)
2. 「つなぐ/つながない/未設定」の設定(会社単位・担当者単位、取次先ごと)
3. 会社・担当者・電話番号の検索と表示
4. 取次メモの登録・一覧・絞り込み・対処済み切り替え
5. 更新者・更新日時の記録(Cloudflare AccessのJWTから取得)

アプリが置き換える範囲: DMやSlackチャンネルでのメッセージ連絡(Slackへの通知機能自体はSTEP2)。

### 2.2 STEP1の対象外(仕様に含めない)【決定】
- Slack通知(宛先への通知を含む)
- 着信記録の自動連携(MacroDroid連携、着信日時の自動取得)
- 迷惑電話・営業電話の自動判定(Google Places API、クチコミサイト参照)
- カレンダー連携
- リアルタイム着信表示
- 権限分け(全員が閲覧・登録可能)
- 工事士com営業チーム宛ての取次(取次先の対象外)

以下は資料上STEP1に含まれるか不明のため、STEP1では作らない前提とした【案】:
- 応対トーク・電話応対テンプレート(「只今不在でして…」等)の表示。ヒアリングの課題の中心なので、意図的な除外としてレビュー会①で確認する(Q-15)。
- 個人情報の物理削除、保管期間、バックアップ(第9回以降の運用ルールで決める。Q-25)。

### 2.3 技術制約(前提)【決定】
- 実行基盤: Cloudflare Workers / D1(SQLite) / Access。Webフレームワークは Hono。
- ローカル開発: Docker + Wrangler。社内標準テンプレートを土台にする。
- フロント: Tailwind CSS + daisyUI、サーバー連携は htmx、小さなクライアント動作は Alpine.js(または hono/jsx/dom)。
- 認証: Cloudflare Access。アプリ側にログインUI・セッション管理を作らない。ログインユーザーは `Cf-Access-Jwt-Assertion` のJWTから取得する。
- セキュリティ必須事項: Accessのバイパス経路(`*.workers.dev`、`*.pages.dev`、プレビューURL)の遮断、アプリ側でのJWT検証。
- D1は書き込みが少ないRead中心の用途向け。利用規模は数十人以下。
- シークレットは `wrangler secret` で管理し、リポジトリに含めない。

## 3. 用語定義

| 用語 | 定義 |
| --- | --- |
| 会社 | 取引先の会社。会社名・よみがな・メモを持つ。 |
| 担当者 | 会社に所属する取引先の個人。氏名・よみがな・電話番号・メモを持つ。 |
| 取次先 | 電話をつなぐ先(社内の人)。対象は社長・菊地・益岡・木村の4名。工事士com営業チームは対象外。【決定】 |

| 自分宛て | ログインユーザーのメールアドレスに対応する取次先が宛先に含まれる取次メモ【案】(Q-20)。 |
| 論理削除 | データを物理削除せず「削除済み」状態にし、復元できるようにすること。 |
| 更新者 | 変更操作を行ったログインユーザー(JWTのメールアドレス)。 |

## 4. ユーザーと利用シーン

### 4.1 ユーザー
- 電話を受ける人【決定】: 菊地さん、制作チーム、松山さん、開発チーム、営業の若手の人(新人を含む)。ヒアリング時の範囲(ISチーム・マーケチーム含む、FS・CS・社長・リモートの人を除く)とは差があり、第3回の範囲を採用する(10.2)。
- 取次先の人【決定】: 社長、菊地、益岡、木村。取次メモを読む側。
- 全員が閲覧・登録・編集できる(権限分けなし)【決定】。取次先の人も電話を受ける人も同じ画面を使う。

### 4.2 利用シーン(アプリが支える流れ)

**A. 登録済みの相手から着信(新人が迷わず対応する流れ)**
1. 電話を受けた人が、相手の電話番号・会社名・氏名のいずれかで検索する。
2. 結果に、取次先4名ごとの実効判定(つなぐ/つながない/未設定)と設定元が表示される。
3. 「つなぐ」の取次先には電話をつなぐ(アプリ外の操作)。「つながない」は取り次がない。
4. つながない場合や不在の場合は、取次メモを登録する。

**B. 判定が「未設定」の場合**【案】
未設定は「判断が未登録」の意味。用件を聞いたうえで取次先に確認する。アプリは未設定と表示するのみで、既定動作は決めない(Q-06)。

**C. 初めての会社からの着信**【補足】
1. 検索して該当なしを確認する(「該当なし」画面から新規登録へ進める)。
2. 用件をヒアリングし、取り次ぐ(ヒアリング資料:「用件をヒアリングの上、繋いでほしい」)。
3. 電話を受けた人が、事後に会社・担当者を登録する。必要なら取次メモも登録する。登録時、取次メモの入力内容を引き継げる。【案】

**D. 取次先の人が自分宛ての取次メモを確認する**【案】(Q-20)
1. 取次先の人がアプリを開くと、自分宛ての未対処の取次メモの件数が画面上部に表示される。
2. 件数から取次メモ一覧へ進み、自分宛ての未対処メモを確認する。
3. 対応したらメモを対処済みにする。
STEP1にはSlack通知がないため、新着に気づく手段はこの件数表示のみ(画面を開いたときに更新。自動更新はしない)。

## 5. 機能要件

### 5.0 共通ルール
- 入力エラー時は保存せず、該当項目の近くにエラーを表示し、入力値を保持する。
- すべての変更操作は更新者・更新日時を記録する(5.7)。
- 本章のメッセージ文言は【案】。
- **競合検知**【案】(Q-14): 会社・担当者・取次メモの編集、つなぐ設定の変更、削除、復元、対処済みの切り替えのすべてで、画面表示時点の版(更新日時)と保存時点の現在の版が異なる場合は保存せず、「他の人が先に更新しました。画面を読み込み直してください」を表示する。つなぐ設定の変更は、確認画面を表示した時点の変更前の値を基準にする。対処済みの切り替えは、一覧表示時点の状態を基準にし、異なる場合は更新せず最新の状態を表示する。
- **二重送信の抑止**【案】: 同じ登録操作が連続して2回送信されても、1件のみ作成される。
- **不正な送信元の拒否**【案】: 状態を変更するリクエストは、アプリの画面からの操作であることを検証し、そうでない場合は403を返して何も変更しない。

### 5.1 認証とユーザー識別 【決定】(FR-AUTH-01)

| 項目 | 内容 |
| --- | --- |
| 概要 | 全リクエストでAccessのJWTを検証し、ログインユーザーを特定する。アプリにログインUIを持たない。 |
| 検証内容 | `Cf-Access-Jwt-Assertion` の存在、署名、有効期限(exp)、audience(aud)。 |
| 振る舞い | 検証に成功した場合のみ画面・データを返す。ユーザーのメールアドレスを更新者として使う。更新者はクライアントから送られた値を使わない。 |
| エラー時 | ヘッダなし・署名不正・期限切れ・aud不一致は401を返し、業務データや画面本文を含めない。画面・htmxの部分更新・APIのすべてが対象。 |
| 部分更新での401 | htmxの部分更新が401になった場合、画面に「ログインの有効期限が切れました。ページを再読み込みしてください」を表示する【案】(Q-24)。 |
| 補足 | JWTにメールアドレスが無い場合も401とする【案】。ローカル開発時のJWTの扱いはテンプレートの方式に従う(Q-17)。 |

### 5.2 会社・担当者の登録/編集

#### 5.2.1 会社(FR-CO-01)【決定:項目 / 案:制約】

| 項目 | 必須 | 制約 |
| --- | --- | --- |
| 会社名 | 必須 | 100文字以内【案】。前後の空白は除去 |
| 会社名よみがな | 任意 | ひらがな・カタカナ・長音・空白のみ。カタカナは保存時にひらがなへ正規化【案】 |
| メモ | 任意 | 1,000文字以内【案】 |

- 振る舞い: 登録・編集ができる。新規登録した会社の全取次先の設定は「未設定」。
- 重複: 正規化会社名(全角半角統一・空白除去・英字大小無視)が既存の有効な会社と一致する場合は警告し、「別の会社として登録する」を確認した場合のみ保存できる(同名の別会社が存在しうるため)【案】(Q-04)。

#### 5.2.2 担当者(FR-CT-01)【決定:項目 / 案:制約】

| 項目 | 必須 | 制約 |
| --- | --- | --- |
| 所属会社 | 必須 | 有効な会社を1つ選択【案】 |
| 氏名 | 必須 | 50文字以内【案】。前後の空白は除去 |
| 氏名よみがな | 任意 | 会社名よみがなと同じ規則 |
| 電話番号 | 任意【案】 | **半角数字のみ。ハイフン・全角数字・空白・英字を含む入力は保存不可**【決定】。15桁以内【案】 |
| メモ | 任意 | 1,000文字以内【案】 |

- 電話番号の保存形式: 先頭の0を保持した数字のみの文字列。保存時に自動変換はしない(エラーにする)。
- 重複【案】(Q-04):
  - 同じ会社内で、正規化氏名が一致し、かつ**両方の電話番号が空でなく完全一致**する有効な担当者がいる場合は登録不可。
  - 同じ会社内で正規化氏名が一致し、どちらかの電話番号が空の場合は警告し、確認した場合のみ保存可(同姓同名の別人がありうるため)。
  - 同じ電話番号が別の担当者(別会社を含む)にある場合は警告し、確認した場合のみ保存可。
- 代表番号の扱い【案】(Q-22): 氏名が分からない相手(会社の代表番号など)は、氏名を「代表」として担当者を登録する。会社自体には電話番号の項目を持たない(第3回の登録情報に従う)。
- 所属会社の変更【案】(Q-23): 編集で所属会社を変更できる(転職・社名変更への対応)。変更先は有効な会社のみ。保存前に変更前後の会社名を示す確認画面を挟む。担当者のつなぐ/つながない設定は担当者に付随して維持し、実効判定は変更先の会社設定で再計算される。変更は変更履歴に残す。
- エラー文言: 「電話番号は半角数字のみ(ハイフンなし)で入力してください」ほか。

### 5.3 削除と復元(FR-DEL-01)【決定:要件 / 案:方式】

- 会社・担当者を削除できる。削除は論理削除とし、物理削除は提供しない(物理削除の扱いはQ-25)。
- 削除済みの会社・担当者を一覧(削除済み一覧)で確認し、復元できる。
- 方式【案】(Q-07):
  - 会社を削除すると、所属する有効な担当者も同時に削除済みにする。会社を復元すると、その削除操作と同時に削除された担当者も復元する。それ以前に個別に削除されていた担当者は復元しない。
  - 担当者のみの削除・復元もできる。削除済みの会社に所属する担当者は、先に会社を復元しないと復元できない。
  - つなぐ/つながない設定は削除時に消さず、復元で削除前の状態に戻る。
  - 復元時の重複判定は5.2のルールと同じ。登録不可に該当する場合は復元できない。警告に該当する場合は、警告を表示し、確認した場合のみ復元できる。
  - 削除済みの会社・担当者に対して、設定変更・編集・取次メモの相手としての選択はできない(「対象が見つかりません」を表示)。
  - 取次メモは削除機能を提供しない(誤入力は編集で修正)。
- 誤操作防止: 削除は、対象名(会社名または氏名)の入力を求める確認画面を経て確定する。入力は、全角半角の統一と空白の除去をしたうえで対象名と完全一致した場合のみ確定できる【案】(Q-08)。
- 削除・復元も更新者・更新日時を記録する。

### 5.4 つなぐ/つながない設定

#### 5.4.1 設定の持ち方(FR-RULE-01)【決定】
- 設定は「対象(会社または担当者)× 取次先(4名)」ごとに、つなぐ / つながない / 未設定の3状態を持つ。(解釈の確認: Q-01)
- 初期状態は全取次先「未設定」。
- 会社単位と担当者単位をそれぞれ独立に設定できる。

例(第3回より):

| 対象 | 菊地 | 社長 |
| --- | --- | --- |
| ミイダス(会社) | つながない | つなぐ |
| マイナビ(会社) | 未設定 | つなぐ |
| マイナビ 原田(担当者) | つながない | つなぐ |

#### 5.4.2 変更時の誤操作防止(FR-RULE-02)【決定:要件 / 案:具体策】
- 参照画面では設定を変更できない状態で表示し、「設定を変更する」操作で編集に入る。
- 保存の前に確認画面を表示する。確認画面には、対象名・取次先・変更前→変更後を表示する。確認の確定操作でのみ保存される。キャンセルした場合は何も変更されない。
- 会社設定の変更の確認画面には、影響範囲として「この変更で実効判定が変わる担当者の人数」(その取次先について担当者設定が未設定の、有効な所属担当者の人数)を表示する【案】。
- 取次先ごとに独立して変更できる(社長の設定変更が他の取次先に影響しない)。取次先は4名以外を指定できない。
- 誤操作防止の具体策はQ-08。

#### 5.4.3 実効判定ルール(FR-RULE-03)【案】(Q-02)
会社設定と担当者設定が食い違う場合の優先ルール。

| 案 | ルール | 長所 | 短所 |
| --- | --- | --- | --- |
| **A(暫定採用)** | 担当者設定が「未設定」以外ならそれを採用。「未設定」なら会社設定を採用。両方未設定なら未設定 | 個別の例外(例: 原田だけつながない)を表現できる。第3回の例と整合 | 会社が「つながない」でも担当者「つなぐ」でつながる |
| B | 取次先ごとに、会社・担当者のどちらかが「つながない」なら「つながない」(安全側) | 誤ってつなぐ事故が減る | 担当者単位で「つなぐ」を例外にできない |
| C | 合成せず、会社設定と担当者設定を並べて表示し、人が判断する | 食い違いを隠さない | 新人が判断に迷う(目的に反する) |

- 暫定のA: 担当者を特定できた場合は担当者×取次先の実効判定を表示する。会社のみ特定できた場合は会社設定を表示する。
- 表示は実効判定に加え、設定元(会社/担当者)と会社・担当者それぞれの元の設定値を併記する。

### 5.5 検索・表示(FR-SRCH-01)【決定:対象 / 案:詳細】

| 項目 | 内容 |
| --- | --- |
| 検索対象 | 電話番号、会社名、氏名、よみがな(会社・氏名) 【決定】 |
| 入力 | 検索語を1つ入力。ハイフン・全角数字を許容し、照合時に半角数字へ正規化する【案】(保存時とは異なり検索は許容) |

| ページング | 1ページ20社。会社を単位とする【案】 |
| 並び順 | ①電話番号が完全一致した担当者の会社を先頭、②それ以外。同順位内は会社名よみがな(なければ会社名)の昇順。会社内の担当者は氏名よみがな(なければ氏名)の昇順【案】 |

| 削除済み | 通常の検索結果に出さない。削除済み一覧でのみ表示 |

### 5.6 取次メモ

#### 5.6.1 登録(FR-MEMO-01)【決定:項目 / 案:制約】

| 項目 | 必須 | 制約 |
| --- | --- | --- |
| 相手の会社名 | 条件付き | 登録済みの相手を選ぶと自動入力(入力不要)【決定】。100文字以内【案】 |
| 相手の氏名 | 条件付き | 同上。50文字以内【案】 |
| 相手の電話番号 | 条件付き | 同上。半角数字のみ、ハイフン不可【決定】。15桁以内【案】 |
| 用件 | 必須 | 折り返し希望 / 連絡があったことをお伝え希望 / 伝言希望 のいずれか1つ【決定】 |
| 伝言 | 用件が「伝言希望」のとき必須【案】、それ以外は任意 | 1,000文字以内【案】 |
| メモ | 任意 | 1,000文字以内【案】 |
| 対処済み | - | 初期値は未対処【決定】 |
| 宛先(取次先) | 必須 | 4名から1名以上を選択【案】(Q-05) |

- 相手情報(会社名・氏名・電話番号)は、3項目のうち1つ以上が必須【案】(Q-10)。電話番号のみ空でもよい。
- 登録済みの相手は、検索結果から選択するか、電話番号などの入力で候補を提示して選択する。選択すると3項目が自動入力される。未登録の相手は手入力で登録できる。
- 候補の提示は6.4の照合ルールに従う。複数候補の場合は自動選択せず、人が選ぶ。候補を選ばなければ未登録の相手として保存される。
- 相手情報は取次メモ側にも保持する(登録済みの会社・担当者が後で変更・削除されても、メモの表示は変わらない)【案】。
- 未登録相手のメモから、会社・担当者の登録画面へ入力内容を引き継いで遷移できる【案】(Q-16)。
- 着信日時は入力項目にしない(着信記録はSTEP2)。メモの登録日時を自動記録する【案】(Q-12)。

#### 5.6.2 一覧・絞り込み・対処済み切り替え(FR-MEMO-02)【決定:要件 / 案:詳細】
- 一覧は新しい順。20件ずつ表示【案】。
- 初期表示【案】(Q-20):
  - ログインユーザーのメールアドレスが取次先に対応する場合: 宛先=自分、未対処のみ(「すべての宛先」へ切り替えられる)。
  - 対応しない場合: 宛先=すべて、未対処のみ。
  - 初期表示を未対処のみとするのは、ヒアリングの「チェックしたら絞り込みから消える」【補足】に基づく。
- 取次先に対応するユーザーには、画面上部に「自分宛ての未対処の件数」を表示し、一覧へ進める【案】(Q-20)。
- 絞り込み条件: 用件、対処済み(未対処のみ/対処済みのみ/すべて)、宛先、キーワード(相手情報・伝言・メモ)【案】。
- 対処済みはメモ1件につき1つ。宛先が複数でも、誰かが対処済みにすればそのメモは全宛先で対処済みになる【案】(Q-21)。対処済みにした人と日時は更新者・更新日時で分かる。
- 対処済みは一覧からワンアクションで切り替えられ、未対処へ戻せる。対処済みの切り替えには確認画面を挟まない(誤操作しても戻せるため)【案】。
- 取次メモも編集できる(相手情報・用件・伝言・メモ・宛先・対処済み)。

### 5.7 更新者・更新日時・変更履歴の記録(FR-AUD-01)【決定:要件 / 案:詳細】
- 会社・担当者・取次メモ・つなぐ設定の各データに、作成者・作成日時・更新者・更新日時を持ち、画面で確認できる。

### 6.3 電話番号の正規化・バリデーション【決定】
- 保存形式: 半角数字のみ。ハイフンを含む値は保存不可(バリデーションエラー)。文字列として扱い、先頭の0を失わない。
- 全角数字・空白・英字・記号はすべて保存不可。保存時の自動変換はしない。
- 桁数の上限は15桁、下限は設けない【案】(Q-09)。携帯・内線などの種別は区別しない。1担当者につき電話番号は1つ【案】(Q-22)。
- 検索入力のみ、ハイフン・全角数字を許容して正規化する【案】。

### 6.4 同一人物判定・重複判定【案】(Q-03、Q-04)
同じ相手の判定には電話番号・会社名・氏名を使う【決定】。具体的な照合ルールは以下を暫定とする。

| 順位 | 条件 | 扱い |
| --- | --- | --- |
| 1 | 電話番号が完全一致 | 候補(強)。複数担当者に一致する場合はすべて提示 |
| 2 | 正規化氏名が完全一致 かつ 正規化会社名が完全一致 | 候補 |
| 3 | 正規化会社名のみ完全一致 | 会社の候補 |

- 完全一致の正規化: 全角半角統一、空白除去、英字大小無視、よみがなはひらがな統一。
- 部分一致は検索画面の絞り込み表示にのみ使い、同一人物の判定(取次メモの自動入力候補)には使わない。
- 候補が複数の場合は順位の高い順に並べて提示し、自動選択しない。0件は未登録として扱う。
- 重複登録の扱いは5.2.1/5.2.2のとおり。

### 6.5 論理削除
5.3のとおり。削除済みデータは通常の検索・一覧・実効判定の対象外とし、削除済み一覧と復元操作でのみ参照する。

## 9. 受け入れ条件

### 9.1 認証・ユーザー識別(FR-AUTH-01)

| ID | 区分 | 検証 | Given | When | Then |

## 11. STEP2への拡張メモ

- 取次メモの宛先は、STEP2でSlack通知先に使える。取次先のマスタにはメールアドレスを持たせてあるため(Q-20)、Slackユーザー識別子も同じマスタに追加できる。
- 着信記録(自動連携)は、電話番号をキーに会社・担当者・取次メモと紐付けられるようにする。電話番号は数字のみの文字列で保存しているため、MacroDroidからの受信値と同じ形式で照合しやすい。
- 迷惑電話の判定フラグは、会社・担当者の属性として追加できる。判定元(自動/手動)を区別できるようにしておく。
- 変更履歴・更新者(メールアドレス)は、STEP2の通知・集計でも再利用できる。
- STEP2のデータ(着信日時など)は取次メモと別の記録として追加し、STEP1の取次メモの項目を変更せずに済むようにする。
