## 1. 概要・目的・成功イメージ

### 1.1 概要
代表電話にかかってきた電話について、「つなぐ/つながない」の判断と、取次メモの記録を支援する社内Webアプリ。取引先担当者の氏名・電話番号などの個人情報を扱う。

### 1.2 目的【補足】
- 営業電話など優先度の低い電話への対応時間を減らす(受ける側・つなぎ先の両方)。
- 電話を受けた人が、かかってきた電話の優先度をその場で判断できる。
- 新人が誰にも聞かずに対応できる。

### 1.3 成功イメージ【補足】
新人が、かかってきた相手を検索するだけで「誰につないでよいか/つながないか」を確認でき、つながない場合や取次先が不在の場合は取次メモを残して終えられる。取次先の人は、自分宛ての未対処の取次メモを一覧で確認できる。DMやSlackチャンネルでの手書きの連絡が不要になる。

注: ヒアリングの課題にある「電話でどう答えるか(応対トーク・テンプレート)」はSTEP1の対象外(2.2、Q-15)。STEP1の成功は「つなぐ/つながないの判断」と「取次メモ」に限る。

## 2. スコープ

### 2.1 STEP1の対象【決定】
1. 会社・担当者の登録/編集/削除(論理削除)
2. 「つなぐ/つながない/未設定」の設定(会社単位・担当者単位、取次先ごと)
3. 会社・担当者・電話番号の検索と表示
4. 取次メモの登録・一覧・絞り込み・対処済み切り替え
5. 更新者・更新日時の記録(Cloudflare AccessのJWTから取得)

アプリが置き換える範囲: DMやSlackチャンネルでのメッセージ連絡(Slackへの通知機能自体はSTEP2)。

### 2.2 STEP1の対象外(仕様に含めない)【決定】
- Slack通知(宛先への通知を含む)
- 着信記録の自動連携(MacroDroid連携、着信日時の自動取得)
- 迷惑電話・営業電話の自動判定(Google Places API、クチコミサイト参照)
- カレンダー連携
- リアルタイム着信表示
- 権限分け(STEP1では全員が閲覧・登録可能。STEP2で分ける想定)【決定・第4回】
- 削除済みデータの復元画面、変更履歴(論理削除のみ。復旧はDB直接)【決定・第4回】
- 工事士com営業チーム宛ての取次(取次先の対象外)

以下は資料上STEP1に含まれるか不明のため、STEP1では作らない前提とした【案】:
- 応対トーク・電話応対テンプレート(「只今不在でして…」等)の表示。ヒアリングの課題の中心なので、意図的な除外として確認する(Q-15)。
- 個人情報の物理削除、保管期間、バックアップ、DB直接の復旧手順(第9回以降の運用ルールで決める。Q-25)。

### 2.3 技術制約(前提)【決定】
- 実行基盤: Cloudflare Workers / D1(SQLite) / Access。Webフレームワークは Hono。
- ローカル開発: Docker + Wrangler。社内標準テンプレートを土台にする。
- フロント: Tailwind CSS + daisyUI、サーバー連携は htmx、小さなクライアント動作は Alpine.js(または hono/jsx/dom)。
- 認証: Cloudflare Access。アプリ側にログインUI・セッション管理を作らない。ログインユーザーは `Cf-Access-Jwt-Assertion` のJWTから取得する。
- セキュリティ必須事項: Accessのバイパス経路(`*.workers.dev`、`*.pages.dev`、プレビューURL)の遮断、アプリ側でのJWT検証。
- D1は書き込みが少ないRead中心の用途向け。利用規模は数十人以下。
- シークレットは `wrangler secret` で管理し、リポジトリに含めない。

## 4. ユーザーと利用シーン

### 4.1 ユーザー
- 電話を受ける人【決定】: 菊地さん、制作チーム、松山さん、開発チーム、営業の若手の人(新人を含む)。ヒアリング時の範囲(ISチーム・マーケチーム含む、FS・CS・社長・リモートの人を除く)とは差があり、第3回の範囲を採用する(10.3)。
- 取次先の人【決定】: 社長、菊地、益岡、木村。取次メモを読む側。
- 全員が閲覧・登録・編集できる(権限分けなし。STEP2で分ける想定)【決定・第4回】。取次先の人も電話を受ける人も同じ画面を使う。

### 4.2 利用シーン(アプリが支える流れ)

**A. 登録済みの相手から着信(新人が迷わず対応する流れ)**
1. 電話を受けた人が、相手の電話番号・会社名・氏名・よみがなのいずれかで検索する。
2. 結果に、取次先4名ごとの会社設定・担当者設定・実効判定が表示される。
3. 「つなぐ」の取次先には電話をつなぐ(アプリ外の操作)。「つながない」は取り次がない。
4. つながない場合や不在の場合は、取次メモを登録する。

**B. 判定が「未設定」の場合**
「未設定」の扱いは別途全社で決める。決まるまで、アプリは「未設定」と表示するのみで、既定動作は決めない【決定・第4回】(Q-06)。

**C. 初めての会社からの着信**【補足】
1. 検索して該当なしを確認する(「該当なし」画面から新規登録へ進める)。
2. 用件をヒアリングし、取り次ぐ(ヒアリング資料:「用件をヒアリングの上、繋いでほしい」)。
3. 電話を受けた人が、事後に会社・担当者を登録する。必要なら取次メモも登録する。登録時、取次メモの入力内容を引き継げる。【案】

**D. 取次先の人が自分宛ての取次メモを確認する**【案】(Q-20)
1. 取次先の人がアプリを開くと、自分宛ての未対処の取次メモの件数が画面上部に表示される。
2. 件数から取次メモ一覧へ進み、自分宛ての未対処メモを確認する。
3. 対応したらメモを対処済みにする。
STEP1にはSlack通知がないため、新着に気づく手段はこの件数表示のみ(画面を開いたときに更新。自動更新はしない)。

## 5. 機能要件

### 5.0 共通ルール
- 入力エラー時は保存せず、該当項目の近くにエラーを表示し、入力値を保持する。
- すべての変更操作は更新者・更新日時を記録する(5.7)。
- 本章のメッセージ文言は【案】。
- **競合検知**【案】(Q-14): 会社・担当者・取次メモの編集、つなぐ設定の変更、削除、対処済みの切り替えのすべてで、画面表示時点の版(更新日時)と保存時点の現在の版が異なる場合は保存せず、「他の人が先に更新しました。画面を読み込み直してください」を表示する。つなぐ設定の変更は、確認画面を表示した時点の変更前の値を基準にする。対処済みの切り替えは、一覧表示時点の状態を基準にし、異なる場合は更新せず最新の状態を表示する。
- **二重送信の抑止**【案】: 同じ登録操作が連続して2回送信されても、1件のみ作成される。
- **不正な送信元の拒否**【案】: 状態を変更するリクエストは、アプリの画面からの操作であることを検証し、そうでない場合は403を返して何も変更しない。

### 5.1 認証とユーザー識別 【決定】(FR-AUTH-01)

| 項目 | 内容 |
| --- | --- |
| 概要 | 全リクエストでAccessのJWTを検証し、ログインユーザーを特定する。アプリにログインUIを持たない。 |
| 検証内容 | `Cf-Access-Jwt-Assertion` の存在、署名、有効期限(exp)、audience(aud)。 |
| 振る舞い | 検証に成功した場合のみ画面・データを返す。ユーザーのメールアドレスを更新者として使う。更新者はクライアントから送られた値を使わない。 |
| エラー時 | ヘッダなし・署名不正・期限切れ・aud不一致は401を返し、業務データや画面本文を含めない。画面・htmxの部分更新・APIのすべてが対象。 |
| 部分更新での401 | htmxの部分更新が401になった場合、画面に「ログインの有効期限が切れました。ページを再読み込みしてください」を表示する【案】(Q-24)。 |
| 補足 | JWTにメールアドレスが無い場合も401とする【案】。ローカル開発時のJWTの扱いはテンプレートの方式に従う(Q-17)。 |

### 5.2 会社・担当者の登録/編集

#### 5.2.1 会社(FR-CO-01)【決定・第4回:必須/任意 / 案:その他の制約】

| 項目 | 必須 | 制約 |
| --- | --- | --- |
| 会社名 | 任意【決定・第4回】 | 100文字以内【案】。前後の空白は除去 |
| 会社名よみがな | **必須**【決定・第4回】 | ひらがな・カタカナ・長音・空白のみ。カタカナは保存時にひらがなへ正規化。100文字以内【案】 |
| 電話番号 | **必須**【決定・第4回】(解釈はQ-26) | **半角数字のみ。ハイフンを含む入力は保存不可**【決定】。15桁以内【決定・第4回】 |
| メモ | 任意 | 1,000文字以内【案】 |

- 振る舞い: 登録・編集ができる。新規登録した会社の全取次先の設定は「未設定」。会社名が空の会社は、よみがなを表示名として使う【案】(Q-27)。
- 重複【案】(Q-04): 正規化会社名(全角半角統一・空白除去・英字大小無視。空でない場合)またはよみがなが、既存の有効な会社と一致する場合は警告し、「別の会社として登録する」を確認した場合のみ保存できる(同名の別会社が存在しうるため)。会社の電話番号が別の有効な会社と同じ場合も、同様に警告して確認した場合のみ保存できる。

#### 5.2.2 担当者(FR-CT-01)【決定・第4回:必須/任意 / 案:その他の制約】

| 項目 | 必須 | 制約 |
| --- | --- | --- |
| 所属会社 | 必須【案】 | 有効な会社を1つ選択 |
| 氏名 | 任意【決定・第4回】 | 50文字以内【案】。前後の空白は除去 |
| 氏名よみがな | **必須**【決定・第4回】 | 会社名よみがなと同じ規則(50文字以内) |
| 電話番号 | **必須**【決定・第4回】 | **半角数字のみ。ハイフン・全角数字・空白・英字を含む入力は保存不可**【決定】。15桁以内【決定・第4回】 |
| メモ | 任意 | 1,000文字以内【案】 |

- 電話番号の保存形式: 先頭の0を保持した数字のみの文字列。保存時に自動変換はしない(エラーにする)。
- 氏名が空の担当者は、よみがなを表示名として使う【案】(Q-27)。
- 重複【案】(Q-04):
  - 同じ会社内で、「正規化氏名(空でない場合)またはよみがなが一致」し、かつ電話番号が完全一致する有効な担当者がいる場合は登録不可。
  - 同じ電話番号が別の担当者(別会社を含む)にある場合は警告し、確認した場合のみ保存可。
- 担当者の氏名が分からない着信は、会社の電話番号で検索・対応する(会社が電話番号を持つため)【決定・第4回】(Q-26)。
- 所属会社の変更【案】(Q-23): 編集で所属会社を変更できる(転職・社名変更への対応)。変更先は有効な会社のみ。保存前に変更前後の会社名を示す確認画面を挟む。担当者のつなぐ/つながない設定は担当者に付随して維持し、実効判定は変更先の会社設定で再計算される。
- エラー文言: 「電話番号は半角数字のみ(ハイフンなし)で入力してください」ほか。

### 5.3 削除(論理削除)(FR-DEL-01)【決定・第4回:論理削除のみ / 案:方式】

- 会社・担当者を削除できる。削除は論理削除とし、物理削除は提供しない【決定・第4回】。
- **削除済みの一覧・復元の画面は作らない。復旧はDBを直接操作して行う**【決定・第4回】(Q-28)。
- 方式【案】(Q-07):
  - 会社を削除すると、所属する有効な担当者も同時に削除済みにする。連動して削除された担当者は、DBで識別できる(DB直接の復旧で、会社と同時に削除された担当者を判別するため)。
  - つなぐ/つながない設定は削除時に消さず、DBに残す。
  - 削除済みの会社・担当者に対して、設定変更・編集・取次メモの相手としての選択はできない(「対象が見つかりません」を表示)。
  - 削除済みデータは通常の検索・一覧・実効判定に含めない。
  - 取次メモは削除機能を提供しない(誤入力は編集で修正)。
- 誤操作防止【決定】: 削除は、対象名(会社名または氏名。空の場合はよみがな)の入力を求める確認画面を経て確定する。入力は、全角半角の統一と空白の除去をしたうえで対象名と完全一致した場合のみ確定できる【案】(Q-08)。
- 削除日時・削除者を記録する。

### 5.4 つなぐ/つながない設定

#### 5.4.1 設定の持ち方(FR-RULE-01)【決定】
- 設定は「対象(会社または担当者)× 取次先(4名)」ごとに、つなぐ / つながない / 未設定の3状態を持つ。(解釈の確認: Q-01)
- 初期状態は全取次先「未設定」。
- 会社単位と担当者単位をそれぞれ独立に設定できる。

例(第3回より):

| 対象 | 菊地 | 社長 |
| --- | --- | --- |
| ミイダス(会社) | つながない | つなぐ |
| マイナビ(会社) | 未設定 | つなぐ |
| マイナビ 原田(担当者) | つながない | つなぐ |

#### 5.4.2 変更時の誤操作防止(FR-RULE-02)【決定:要件 / 案:具体策】
- 参照画面では設定を変更できない状態で表示し、「設定を変更する」操作で編集に入る。
- 保存の前に確認画面を表示する。確認画面には、対象名・取次先・変更前→変更後を表示する。確認の確定操作でのみ保存される。キャンセルした場合は何も変更されない。
- 会社設定の変更の確認画面には、影響範囲として「この変更で実効判定が変わる担当者の人数」(その取次先について担当者設定が未設定の、有効な所属担当者の人数)を表示する【案】。
- 取次先ごとに独立して変更できる(社長の設定変更が他の取次先に影響しない)。取次先は4名以外を指定できない。
- 誤操作防止の具体策はQ-08。

### 6.4 同一人物判定・重複判定【案】(Q-03、Q-04)

| 順位 | 条件 | 扱い |
| --- | --- | --- |
| 1 | 電話番号が完全一致(担当者または会社) | 候補(強)。複数に一致する場合はすべて提示 |
| 2 | 正規化氏名が完全一致(空でない場合) かつ 正規化会社名が完全一致(空でない場合) | 候補 |
| 3 | 正規化会社名のみ完全一致(空でない場合) | 会社の候補 |

## 9. 受け入れ条件

形式はGiven/When/Thenに統一する。
- 「区分」は元になる要件の区分(【案】はQ-xxの確定で変わりうる)。「決定」には第4回の決定を含む。
- 「検証」は確かめ方。**自動**=ユニット/APIテスト/E2Eでループから自動実行できる、**手動**=人が目視・実機で確認、**デプロイ後**=デプロイした環境で確認。
- エラー文言は5章の案に従う。
- IDの欠番は、第4回の決定で不要になった条件を削除したもの。

### 9.0 共通受け入れ条件との関係【決定・第4回】
- 第4回で、Must機能について全員共通の受け入れ条件(共通AC)を決める。共通ACは、masuoka-hcompany/call-memo-book の `docs/spec.md` をベースに抜粋し、「受け入れ条件の索引」まで共通とする。Given/When/Thenまでは揃えない。後日すり合わせる(Q-31)。
- 共通ACの対象はMust機能のみ。「共通ACがすべて通過すればSTEP1完成」に全員が合意する。
- 各自が追加した機能のACは各自の仕様書に残し、共通にはしない。
- 本書のACと共通ACの対応表は、共通ACの索引が確定した後に追加する(未反映)。

本書のAC群とMust機能の対応:

| 区分 | 機能 | 本書のAC |
| --- | --- | --- |
| Must | 取引先(会社・担当者)の登録 | 9.2、9.3 |
| Must | 取次設定(つなぐ/つながない) | 9.4 |
| Must | 相手の検索と取次可否の表示 | 9.5 |

## 11. STEP2への拡張メモ

- 権限分けはSTEP2で検討する(第4回)。STEP1の更新者(メールアドレス)と、取次先とメールアドレスの対応(Q-20)が土台になる。
- 取次メモの宛先は、STEP2でSlack通知先に使える。取次先のマスタにはメールアドレスを持たせてあるため(Q-20)、Slackユーザー識別子も同じマスタに追加できる。宛先は1名のため、通知先は1メモにつき1人になる。
- 着信記録(自動連携)は、電話番号をキーに会社・担当者・取次メモと紐付けられるようにする。電話番号は数字のみの文字列で保存しているため、MacroDroidからの受信値と同じ形式で照合しやすい。STEP1の受電日時(受電者が入力)とSTEP2の着信日時(自動取得)の関係は、STEP2の要件精緻化で決める。
- 迷惑電話の判定フラグは、会社・担当者の属性として追加できる。判定元(自動/手動)を区別できるようにしておく。
- 変更履歴(変更前後の値の記録)はSTEP1では作らない(第4回)。必要になった場合はSTEP2以降で検討する。更新者・削除者はSTEP2の通知・集計でも再利用できる。
- STEP2のデータ(着信日時など)は取次メモと別の記録として追加し、STEP1の取次メモの項目を変更せずに済むようにする。
